# Схема данных

Единый бинарный контракт системы. Определяет структуру всех пакетов между узлами.

## 1. Потоки

Протокол разделён на два однонаправленных потока.

- **CaptureEventPacket** - передаёт сырые данные CV-моделей и управляющие события в вычислительное ядро.
- **RigUpdatePacket** - передаёт готовый скелет, готовый к наложению на 3D-модель.

## 2. Карта резервированных тегов

**1-2** - транспортные метаданные вне `one payload`.
**3-5** - системный блок и контрольные данные.
**6-9** - данные о захвате тела, рук и лица.
**10-15** - объекты и окружение, а также дополнительный резерв в случае нехватки основного протокола.

Пример:

- `1: timestamp`
- `2: actor_id`
- `3: handshake`
- `4: status`
- `5: config`
- `6: body`
- `7: left_hand`
- `8: right_hand`
- `9: face`
- `10: props`

> Важно не превышать диапазон 1-15, чтобы не выйти за размер более 1 байта.

## 3. Архитектурные решения

- Префикс `Proto` для базовых математических типов `ProtoVector3` и `ProtoQuaternion` был выбран в связи с резервированием `Vector3` и `Quaternion` в игровых движках для избежания конфликтов.
- Плоская упаковка координат (в канале `Capture` -> `Core`) удобна для масштабируемости данных в случае их нехватки или необходимости добавления новых при обработке разных CV-моделей. Выбран шаг в 4 числа для упаковки [x, y, z, visibility].
- Пакеты не передают наименования костей или точек. Порядок определяется индексом массивов и соответствует их официальной документации.
- Сокет всегда принимает один набор данных из `oneof payload` для сохранения атомарности и соответствия ограничениям MTU, передавая либо тело, либо руки, либо лицо.

## 4. Кодогенерация

Схема компилируется в нативные типы каждого узла соответствующими инструментами.

Пути сохранения схем:

- `capture/web/src/types/schema.ts`
- `core/build.rs`
- `visualizer/proto/schema.pb.gd`

## 5. Открытые вопросы

- Передача параметров кадра вроде соотношения сторон, чтобы избежать искажений пропорций скелета.
